# Keep — STYLE.md

UI/UX pattern reference, in the spirit of Beacon's `STYLE.md`. Deliberately starting minimal — Beacon's grew to its current size organically, one documented pattern at a time, as real pages were built. This file should grow the same way: when a new reusable pattern is established (a list-page shell, a form-page shell, a filter-chip bar, etc.), document it here with the markup/CSS/script shape, not just leave it implicit in the component that happens to use it first.

## Design tokens

`src/app.css` — ported verbatim from Beacon's `dashboard/src/style.css` token block (`--color-*`, `--r-*`, `--font`, `--mono`, etc.). Keep these two files' values in sync across the product suite.

## Established patterns so far

- **List page shell**: `.section-card` > `.section-card-head` (title + `.row-count-badge`) > plain `<table>`. See `(admin)/users/+page.svelte` once built.
- **Full-page create/edit form shell**: `.pf-page`/`.pf-crumb`/`.pf-topbar`/`.pf-body`/`.pf-group`/`.pf-group-title`. One route serves both create and edit.
- **Modal**: `.modal-backdrop`/`.modal`/`.modal-header`/`.modal-body`/`.modal-footer` — no direct Beacon precedent (Beacon styles modals per-page); defined generically in `app.css` for Keep's API-key reveal-once dialog and confirmations.
- **Sidebar accordion nav**: ported from Beacon's `App.vue` collapsible-section sidebar (`.sec-head`/`.sec-body`/`.sbi`/`.sec-chevron`, `sec-head` click toggles that section's body — multiple sections can be open at once, it's not a single-open accordion). Data-driven via `src/lib/navigation.ts`'s `NAV_SECTIONS` catalog, rendered by `src/lib/components/Sidebar.svelte`; a section's links can be flat (`links`) or organized into labeled sub-clusters (`groups`, e.g. Admin's "Service Desk"/"Access" clusters) so a section doesn't itself recreate the same crowding problem as it grows. Contracts proved the extension path: a new top-level catalog entry, route set, and static `Icon.svelte` icon required no sidebar-shell or shared nav CSS changes. Icons are hand-authored inline SVG, not a library dependency.
- **Column chooser**: a per-user, server-persisted list-column customizer — `src/lib/ticketColumns.ts`'s `TICKET_COLUMNS` catalog (same "const array of typed objects with a stable key" idiom as `NAV_SECTIONS`/`WIDGET_TYPES`) + `src/lib/components/ColumnChooserModal.svelte` (a two-pane Available/Selected picker with move/reorder buttons, built on the generic `.modal-*` classes) + a `saveColumns` form action persisting to a per-user nullable JSON column (`users.ticketColumnPrefs`, resolved via `resolveVisibleColumns()` with a safe default fallback). The list page itself renders columns by switching on `column.key` inside the row loop — the same render-by-switching-on-a-key idiom `Icon.svelte` established, since Svelte can't pass arbitrary render functions through a plain data array. The trigger button lives inside `.section-card-head` next to the row-count badge (not the page's `.pf-topbar`) — it's a view control for *this table*, not a page-level action like "+ New Ticket". Give it an icon (`Icon name="columns"`, sized via the `.btn-icon` class) rather than text alone. See `(app)/tickets/+page.svelte` for the reference implementation before adding a chooser to another list page.
- **Sortable table headers + pagination footer**: click a `<th>` to sort by it (`.sortable-th` — `cursor:pointer`, hover lightens text); the active column shows a small chevron (`Icon name="chevron"` at `.sort-chevron` size, rotated via a `.is-asc` class toggle, not an inline `style` prop — `Icon.svelte` doesn't forward `style`) pointing up for ascending, down for descending. A column with no single sortable value (e.g. a client-computed badge like SLA state) simply gets no `sortable-th` class/handler — stays plain text, no pointer cursor. Below the table, a `.pagination` bar (border-top, mirroring `.section-card-head`'s border-bottom) holds "Showing X–Y of Z" text (`.pagination-info`) on the left and Prev/Next `.btn.btn-ghost.btn-sm` buttons (disabled at the boundaries — `.btn:disabled` is already generic) plus a "Rows per page" `<select>` on the right. All four classes (`.sortable-th`, `.sort-chevron`, `.pagination`, `.pagination-info`) live in `app.css`, not a scoped per-page `<style>` block, specifically so the next list page that adds sorting/pagination can reuse them directly — see `(app)/tickets/+page.svelte` for the reference implementation.
- **Ticket-number treatment**: always preserve and expose the full stored `T-YYYYMMDD-XXXX` identifier, but render it with `TicketNumber.svelte`: the `T-YYYYMMDD-` namespace/date is muted and the daily sequence is emphasized. This keeps references unambiguous without letting the prefix dominate dense tables. Use `size="inherit"` in headings and the default small size in tables/dashboard lists.
- **Ticket workspace**: ticket detail content is a responsive three-column widget canvas, not a single form column. It lives in the authenticated `(workspace)` route group, outside the main app shell; ticket links open it in a separate browser window via `openTicketWorkspace()`. `src/lib/ticketWorkspace.ts` is the stable widget/preset catalog and defensive versioned-layout parser; `TicketWorkspaceEditor.svelte` is shared by the admin organization-default editor and technician personal customizer. Core widgets cannot be hidden; optional widgets may be hidden and restored. User preferences are server-side and nullable—null follows the current organization default. Keep width choices constrained to coherent presets and preserve the narrow/wide/narrow hierarchy; at tablet/mobile breakpoints the rails collapse rather than squeezing their contents.
- **Ticket editing hierarchy**: ticket workspace widgets present structural data read-only by default. One page-level Edit Ticket control exposes title/description, customer/contact/contract, and classification in a consolidated panel with one save. Low-risk frequently changed pickers such as Assignment autosave and show lightweight Saving/Saved state. Creation actions (notes/time) and workflow transitions (triage/status) remain explicit—do not autosave actions with larger operational consequences.
- **Ticket record composers**: use one text area plus an Internal note checkbox for notes; checked is the safe default and unchecked is client-visible. Keep time entry out of the permanent canvas: Activity opens a wide, sectioned modal while the Time Summary rail remains read-only. The full time form groups time details, inherited billing context, customer-facing/internal notes, and optional workflow change; calculate duration from organization-local start/end values and persist exact UTC instants.
- **Activity quick-add and time summary**: Activity owns the New Note and New Time Entry actions; do not duplicate the time-entry launcher in a rail widget. The Time Summary rail is display-only (worked, estimated, remaining). The full time modal uses the Autotask-informed six-day strip and draggable timeline as its primary date/time selector, with manual start/end inputs kept in sync and a calendar fallback.
- **Directory list controls**: the Companies page is the lighter-weight list pattern for stable business records: a prominent search field, two compact labeled filters, alphabetical default sorting, fixed useful columns, and the shared pagination footer. Search/filter/sort/page state stays in URL params; page size is remembered server-side. Do not add a column chooser simply because the table pattern supports one — Companies deliberately favors a curated summary (company, primary contact, type, SLA, status) over ticket-style configurability. Empty databases say "No companies yet"; filtered empty results explain that nothing matched and offer a visible Clear filters action. See `(app)/(admin)/companies/+page.svelte`.

Add to this list as pages get built — don't let patterns stay undocumented just because "the code is the source of truth." The whole point of this file (per Beacon's own experience) is to make patterns visible to an AI assistant or new contributor without having to reverse-engineer them from five different pages first.
