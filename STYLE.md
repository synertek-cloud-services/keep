# Keep — STYLE.md

UI/UX pattern reference, in the spirit of Beacon's `STYLE.md`. Deliberately starting minimal — Beacon's grew to its current size organically, one documented pattern at a time, as real pages were built. This file should grow the same way: when a new reusable pattern is established (a list-page shell, a form-page shell, a filter-chip bar, etc.), document it here with the markup/CSS/script shape, not just leave it implicit in the component that happens to use it first.

## Design tokens

`src/app.css` — ported verbatim from Beacon's `dashboard/src/style.css` token block (`--color-*`, `--r-*`, `--font`, `--mono`, etc.). Keep these two files' values in sync across the product suite.

## Established patterns so far

- **List page shell**: `.section-card` > `.section-card-head` (title + `.row-count-badge`) > plain `<table>`. See `(admin)/users/+page.svelte` once built.
- **Full-page create/edit form shell**: `.pf-page`/`.pf-crumb`/`.pf-topbar`/`.pf-body`/`.pf-group`/`.pf-group-title`. One route serves both create and edit.
- **Modal**: `.modal-backdrop`/`.modal`/`.modal-header`/`.modal-body`/`.modal-footer` — no direct Beacon precedent (Beacon styles modals per-page); defined generically in `app.css` for Keep's API-key reveal-once dialog and confirmations.
- **Sidebar accordion nav**: ported from Beacon's `App.vue` collapsible-section sidebar (`.sec-head`/`.sec-body`/`.sbi`/`.sec-chevron`, `sec-head` click toggles that section's body — multiple sections can be open at once, it's not a single-open accordion). Data-driven via `src/lib/navigation.ts`'s `NAV_SECTIONS` catalog, rendered by `src/lib/components/Sidebar.svelte`; a section's links can be flat (`links`) or organized into labeled sub-clusters (`groups`, e.g. Admin's "Service Desk"/"Access" clusters) so a section doesn't itself recreate the same crowding problem as it grows. Adding a future top-level module (Contracts, Timesheets, ...) is one more `NAV_SECTIONS` entry plus its routes — no changes to `Sidebar.svelte`/`app.css` needed. Icons are hand-authored inline SVG in `src/lib/components/Icon.svelte` (Beacon's exact path data reused where the concept maps 1:1 — gear, grid, chevron), not a library dependency.
- **Column chooser**: a per-user, server-persisted list-column customizer — `src/lib/ticketColumns.ts`'s `TICKET_COLUMNS` catalog (same "const array of typed objects with a stable key" idiom as `NAV_SECTIONS`/`WIDGET_TYPES`) + `src/lib/components/ColumnChooserModal.svelte` (a two-pane Available/Selected picker with move/reorder buttons, built on the generic `.modal-*` classes) + a `saveColumns` form action persisting to a per-user nullable JSON column (`users.ticketColumnPrefs`, resolved via `resolveVisibleColumns()` with a safe default fallback). The list page itself renders columns by switching on `column.key` inside the row loop — the same render-by-switching-on-a-key idiom `Icon.svelte` established, since Svelte can't pass arbitrary render functions through a plain data array. See `(app)/tickets/+page.svelte` for the reference implementation before adding a chooser to another list page.

Add to this list as pages get built — don't let patterns stay undocumented just because "the code is the source of truth." The whole point of this file (per Beacon's own experience) is to make patterns visible to an AI assistant or new contributor without having to reverse-engineer them from five different pages first.
